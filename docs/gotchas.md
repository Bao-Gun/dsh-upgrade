# 坑

只追加，不整理。一条一行：什么情况下会踩 → 为什么 → 怎么绕。
整理过的坑会失真，宁可粗糙也别汇总成「注意事项」。

- 升级到 `@deepseek-ai/dsh@0.2.3-alpha.2` 后 `dsh web` 起不来（npm 装得上，进程启动即退） → 该版本 `engines.node` 是 `^24.22.3 || >=26.13.1`，本机 node v26.7.0 落在空档里，npm 只告警不拦；0.2.2-rc.5 的 `>=24.9.0` 则满足 → 升级前必须用目标版本 manifest 的 `engines.node` 先校验（`src/server/upgrade.ts` 在备份之前调 `satisfiesNodeRange`，失败文案由 `src/server/versions.ts` 的 `describeEnginesFailure` 生成），不满足就停在 precheck，别装。
- 升级或回滚进行到一半进程被杀，`dsh web` 再也起不来（安装目录缺失或残破，重装前连 npm 都找不到已装包） → `src/server/upgrade.ts` 的回滚是 `rm -rf installDir` 之后才 `rename(backup → installDir)`，两步之间不是原子的；此时磁盘上是「安装目录缺失或残破（`rm` 到一半、`npm` 装到一半都算）、`~/.dsh/dsh-upgrade/backup/<from>` 有完整备份、`pending.json` 还在、`last.json` 停在 `running:true`」 → 别重装、别删备份，先 `rm -rf <安装目录>`（残破目录下直接 `mv` 会把备份挪成 `<安装目录>/<from>`，看着恢复了其实还是坏的）再 `mv ~/.dsh/dsh-upgrade/backup/<from> /opt/homebrew/lib/node_modules/@deepseek-ai/dsh`（或 `npm i -g @deepseek-ai/dsh@<from>`）把树恢复，启动确认后清掉 `pending.json`。
- 改了被文档点名的源文件（如 `src/client/panel.ts`）却没同批改 `docs/architecture.md` → `.githooks/pre-commit` 做反向漂移检查：`grep -rlF` 在 `docs/`、`specs/` 里找引用，发现被改的 src 文件被某份文档点名、而这份文档不在本次暂存里就拦提交（本轮 Task 2-4 因此多次 `--no-verify`，文档债堆到 Task 5 才清） → 改哪个模块就同批改 architecture.md 对应那段；真要拆批次，把文档一并暂存，别累积 `--no-verify`。
- 点完「全部升级」列表不会自己重查 → `startBatch` 的 names 与行文案都取自点击瞬间的插件快照，升完行还停在旧的「x → y」，第二次点「全部升级」会把已升过的包再 POST 一遍（R47 已知边界，本轮不实现自动重查） → 判下一轮之前先关面板重开（`openPanel` 会重新拉一次插件列表）再决定还升不升；别在同一个面板上连点。
- 批量升级中途关面板只停队列，不停当前这个包 → `cancelled: () => view.closed` 只在每个包起包前查一次，已经在飞的包会继续轮询到终态，结果因 `live()` 为假被丢弃，宿主侧操作仍在跑 → 关面板后别马上重开再点「全部升级」，否则新批次起的包可能撞宿主 `OPERATION_BUSY`（该包 failed、其余 skipped）；等一会儿或先看插件是否已经升好。
- 批量轮询的两个时间尺度别混 → 单个操作 `stalledWaitMs`（默认 3 分钟）内没有任何推进就会被判卡住；每个包另有 `MAX_POLLS` 1500 次 × 800ms ≈ 20 分钟的轮询上限（`MAX_POLLS` 在 `upgradeOne` 内部按包重置，**整批没有总上限**） → 别把 3 分钟或 20 分钟当成整轮上限：7 个包都卡住时整批最坏约 2 小时+，期间关面板也不会停当前包（见上一条「中途关面板」）。
- 底栏入口「刷新后还在」不是缓存 → 页面加载时静默查询比底栏渲染快：实测临时实例上查询 t≈100ms 就回来（`/dsh-upgrade/api/status` 与 `/dsh-market/api/v1/updates/summary` 都 200），而按钮 t≈420ms 才被观察器插进座位；`setEntryState` 那一刻 DOM 里还没有按钮，等于什么都没设，之后也没人重设 → 状态记进 `entryStates`（WeakMap），`mountFooterEntry` 的 `settle()` 一插上就 `paintEntry` 重画（R57）。别再往浏览器缓存上找原因：bundle URL 带 `rev=`（文件 mtime/size 算出来的），重建后 rev 会变，缓存不会让你看到旧代码。
- 仓库里构建产物没跟着源码走，索引里写得再对也装不起来 → git 源安装是「下载那个 commit 的 tar」，不跑 prepare、不装 devDependencies，`lib/*.js` 没提交就等于装了个空壳（package.json 的 exports 指向不存在的文件） → 发版顺序永远是「改版本号 → `npm run build` → 提交（含 `lib/*.js`）→ push → 再让索引仓重扫」，`.gitignore` 保持 `/lib/*` + `!/lib/*.js`；只提交源码不提交产物是最容易漏的一步。
- 底栏入口按用户要求「没更新就藏起来」，藏起来后这是唯一入口 → `setEntryState` 用 `visible = hasUpdate || busy || known === false` 判断，`known` 来自 `probeEntryState`（只有 reply.ok 且 plugins 拿到才为真）；`src/client/index.ts` 每 5 分钟（`ENTRY_REFRESH_MS`）静默复查 → 改这块时留神两点：别把 `known === false`（查不到）也当没更新藏掉，否则一次网络失败就再也打不开面板；`stop()` 里必须 `clearInterval`，否则热重载会叠出多个定时器。
- NAS 上升级 dsh 会「装到别处再回滚」 → 宿主 `npm prefix -g` 是 `/home/admin/.local`（可写），而 dsh 在 `/usr/local/lib/node_modules`（root 所有），照 npm 的全局前缀装必然让版本校验不符 → `src/server/npm.ts` 只从 installDir 反推 `--prefix`（只认 `<prefix>/lib/node_modules/@deepseek-ai/dsh` 这一种形状，推不出就 `INSTALL_FAILED`，绝不退回让 npm 自己决定）；npm 走绝对路径、子进程 PATH 头部补 `dirname(process.execPath)`，因为 systemd 用户服务拉起的进程 PATH 里未必有 node/npm。
- Linux 上 GNU cp 没有 `-c`，旧写法「先试 `cp -c -R`、失败再回退 `cp -R`」在 Linux 上第一次必然 `cp: invalid option -- 'c'` → 白跑一趟还往 stderr 留一行噪声，别把这种试错当平台探测 → 平台差异收进 `src/server/clone.ts` 的候选表（darwin `-c`、linux `--reflink=auto`、其它 `-R`，绝不用硬链接），`scripts/install.mjs` 有同一张表、由 `test/clone.test.ts` 动态 import 逐项钉住。
- 只查 `<prefix>/lib/node_modules` 可写还不够，NAS 上照样会晚失败 → `npm i -g --prefix <p>` 除了解包还会往 `<p>/bin` 写 bin 链接（`<p>/bin/dsh`），那一处的权限与 lib 不一定相同（`/usr/local/lib` 与 `/usr/local/bin` 在部分发行版分属不同组），包能装上、链接时才 EACCES，于是又走一遍「备份几百 MB → 版本校验不符 → 整轮回滚」 → `src/server/upgrade.ts` 的可写性检查按 installDir → `<prefix>/lib/node_modules` → `<prefix>/bin` 顺序问，第一个不可写就报 `INSTALL_DIR_NOT_WRITABLE`；判断用 `access(W_OK)` 并对 ENOENT / EACCES / 任何异常都返回 false，检查本身不能成为新的崩溃点。
- Linux 上升级完成后没有系统通知，也不报错 → `osascript` 是 macOS 专属，Linux 上 spawn 必然 ENOENT，而通知按设计静默失败（不崩、也没人发现） → 平台分支收进 `src/server/notify.ts` 的 `notifyCommand`：darwin 走 `osascript`、linux 走 `notify-send`、其它平台空 argv 返回 false；没有图形会话时 `notify-send` 自己失败，同样只是 false。
- 「安装目录不可写」提示里那句「（属主不是你）」只是最常见原因的猜测，不是判定依据 → 判定只看 `access(W_OK)`：ENOENT（目录被删 / 路径拼错）、只读挂载、ACL 拒绝都会进同一个错误码，属主其实是你时也会失败 → 别照着「属主」去 chown，按第一行给出的具体路径查权限 / 挂载 / 路径是否存在。
- 错误消息里给的 `sudo npm i -g --prefix …` 假定 root 的 `secure_path` 能解析到 npm → 有的发行版 sudo 重置 PATH 后找不到 npm（报 `sudo: npm: command not found`），而 node 明明装着 → 改用 `sudo $(command -v npm) i -g --prefix <prefix> @deepseek-ai/dsh@<target>`，绝对路径在 sudo 下照样能执行；但若 npm 来自 nvm（`#!/usr/bin/env node` 脚本），sudo 重置 PATH 后仍可能 `env: node: No such file or directory`，还得让 sudo 的 PATH 里能找到 node。
- 通知子进程没有超时 → `runNotifyDefault` 只等 `close`，`notify-send` 在无 DBus / 桌面会话异常时可能一直挂着，那条 fire-and-forget 就永远 pending（`src/index.ts` 里是 `void …`，不阻塞插件启动，也没有别人来收尾） → 通知只是锦上添花，别为它加阻塞式等待；排查「升级后没通知」先手动跑一次 `notify-send` 看它能不能返回。
- 国内机器上直连 GitHub 会挂死，pnpm 的 git 依赖因此装不完 → NAS 上 `git ls-remote https://github.com/…` 45s 无输出（SOCKS 隧道当时也不通），pnpm 卡在 `Progress: resolved 10` 不动，30 分钟也不报错 → 装 git spec 时用一次性环境改写走 ghproxy，不要动全局 git config：`GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=url.https://ghproxy.net/https://github.com/.insteadOf GIT_CONFIG_VALUE_0=https://github.com/ dsh plugin --profile web add "github:Bao-Gun/dsh-upgrade#<commit>"`（7.2s 装完）；测完把见到的 URL 形态、耗时记进 `docs/nas.md`。
- npm 11 在 Linux 上默认不跑依赖的 install-scripts → 手工 `npm i -g --prefix <p> @deepseek-ai/dsh@<ver>` 会警告 `@deepseek-ai/dsh-subprocess-local, koffi, node-pty, @google/genai, protobufjs` 的 postinstall 被跳过，`dsh --version` 却照常输出（所以探针发现不了） → 排查「装完终端 / 原生模块不对」先看这条警告，需要时 `--allow-scripts=<包名列表>`；插件自己的升级走同一套 npm，遇到同类毛病先怀疑这里而不是版本比对。
- 重启链的预检偶尔第一次就红 → NAS 上首跑 `POST /dsh-restart/api/precheck` 14.7s 且 `stage: boot, ok: false`（试跑实例 12s 内没打印 Web URL，stdout 混着 MCP 的提示噪声），立刻重跑 10.4s 就 `ok: true, health: true` → 这是 dsh-restart 侧冷启动抖动，不是本插件的判定；`runRestartChain` 读到 `ok:false` 就不重启是正确行为，人看到「预检没过」时先重试一次再判断。
- 刚重启完的 1～2 秒内 `/health` 已经 200、插件路由却还没注册 → 紧接着 `GET /dsh-upgrade/api/status` 拿到空响应（curl 退出码 7/空 body），等 8 秒再查就正常 → 重启后的自动检查别只看 `/health`，要留重试窗口；`scripts/install.mjs` 的 pollReady 同理，别把第一次空响应当插件挂了。
- 「继续升级」把上一轮已升级的行刷成空白 → `startBatch` 原来按 `view.rows` 全量 `paintBatchItem` 成 `pending`，可这一轮只跑 `retryNames`（失败的包），已升级那几行清掉后没人再画（复现：a 成功、b 失败 → 点继续升级，a 行变空） → 清 `pending` 只能按这一轮的名单走，不在名单里的行保持上一轮结论。
- 升级面板里正经版本号变成了 40 位 commit（例：`08f9424…b50 → ab4f8cd…e86`）→ 从索引装的插件，spec 是 `github:Bao-Gun/dsh-upgrade#<commit>` 这种**钉死 ref**；dshmarket 的 `gitVersionUpdate`（`lib/updates.js`）遇到显式 ref 直接返回 null，放弃比较 `package.json` 里的 semver，退化成比 commit，于是把两端的 sha 当版本名报给面板（`installedVersion`/`latestVersion`），主分支上任何一次提交都算「有新版本」，哪怕只是文档提交 → 面板这侧 `src/client/panel.ts` 的 `compactVersion` 只把 40 位 sha 缩成前 7 位、全文进 title，别指望市场自己给出版本号：它按设计放弃了这条路径 → 要版本号只能自己补一步，`src/server/plugininfo.ts` + `/dsh-upgrade/api/plugin-version` 做这件事：已装版本读 profile 里 `node_modules/<name>/package.json`，目标版本按 spec 认出 GitHub 仓库再取 `<commit>/package.json`；**这一步要联网**，Mac 上 raw.githubusercontent 能通，NAS 上只有 ghproxy 通，所以 `RAW_BASES` 两站依次试、失败就回短哈希（这一行本来就能看，不值得报错）；同一 commit 缓存 10 分钟。—— 另一条路是让上游对钉死 ref 也读远端版本，或在 profile 里改成浮动 spec（`github:Bao-Gun/dsh-upgrade`），前者不是本插件能修的。
- 预检的 boot 阶段可能在 12s 门槛上连续失败，而重启本身不依赖它 → NAS 上装到 12 个插件后，`POST /dsh-restart/api/precheck` 连跑两次都是 `stage: boot, ok: false`（试跑实例 12s 内没打印 Web URL，stdout 混着 `chrome-devtools-mcp` 的提示），而 `/dsh-restart/api/restart` 照样返回 202、重启后 `/health` 立即 200 → 预检只写一份记录（`saved: true` + fingerprint），不是重启的前置闸门；面板里「预检没过就不重启」是给人的安全带，命令行上想直接换服务可以绕过，但绕过前先确认真的是超时、不是配置/兼容红。
